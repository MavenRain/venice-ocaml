# M31 protocol probe and replay

Base: `ed73670`, the committed M30 encrypted request path.

M31 adds a fixed-public-prompt protocol diagnostic and independent replay
checks. No successful live Venice capture was made because `VENICE_API_KEY`
was absent. Live W11 receipt and W13 framing confirmation remains pending.
The committed transcript is synthetic, generated with public test scalars.
This slice changes no production OCaml API or session admission rule.

## Decisions and evidence

The probe uses the current official guide's secp256k1 ECDH, HKDF-SHA256 with
empty salt and `ecdsa_encryption` info, and AES-256-GCM with empty AAD. Request
and response frames carry a 65-byte public key, 12-byte nonce, ciphertext and
final 16-byte tag. A response key is derived from each frame's server public
key and the client's retained scalar, independently of the request prompt key.

Sources are the [Venice guide](https://docs.venice.ai/guides/features/tee-e2ee-models)
(checked 2026-09-06) and the pinned
[producer](https://github.com/nearai/private-ml-sdk/blob/25c25025c556ab2f797eeda3bab433f38a8ffb7a/vllm-proxy/src/app/api/v1/openai.py#L80).
The producer hashes original request bytes and all encoded SSE text chunks.
The oracle reconstructs the colon-joined hashes from the actual captured bytes,
then verifies ECDSA EIP-191 with recovery or raw Ed25519. The live driver uses
ECDSA. A request ID is bound by the signed SSE body and selects the receipt
route; the formula has no third request-ID field.

The producer returns `text`, `signature`, `signing_address`, `signing_algo`.
Venice's route may transform its upstream data. The pinned
[consumer](https://github.com/elkimek/venice-e2ee/blob/59e5483eed99d1529d5ce3385171b4ba405ac182/src/receipt.ts#L127)
distinguishes wire and cleartext hashes and permits receipt variants without
top-level signatures. Such variants do not confirm the tested formula and
must fail this probe. No alternative formula is selected from receipt fields.

## Trust and capture boundary

The diagnostic accepts no private prompt input. It checks model capability,
challenge echo and structural signing-key/REPORTDATA consistency, but does not
perform full signed TDX, collateral, TCB, measurement or GPU verification.
It mints no SDK `Attested.t` or `Session.t`. M29's CPU-only deployment assertion
and CRL/NRAS limitations are unchanged.

The API key reaches curl only in a config on stdin. Curl starts with `-q` to
ignore user configuration, does not follow redirects or use a proxy, and runs
with a reduced environment. HTTP output is bounded; diagnostic errors exclude
server bodies and curl stderr. The encrypted POST is never retried.

Only a successful run writes an exclusive mode-0600 artifact. Public signing
identity, the exact encrypted request/SSE bytes and allowlisted receipt data
are retained. Credentials, raw HTTP headers, arbitrary attestation envelopes,
private scalars, derived keys and decrypted output are excluded. Modifying the
encrypted transcript invalidates its receipt, so redaction happens by
omitting unrelated fields rather than rewriting signed bytes.

Secretless live replay verifies signatures, byte hashes and frame structure.
It cannot repeat GCM authentication because the scalar was never saved.
Stored summaries cannot substitute for independently recomputed evidence.

The SSE diagnostic accepts one choice, encrypted `content` and
`reasoning_content`, empty-string role metadata, bounded fingerprint/usage
metadata, a finish event and terminal `[DONE]`. It rejects unsupported event
shapes, plaintext content, changing identity and incomplete streams. It is
not the general production SSE decryptor planned for M32.

## Validation

The new suites pass 28 replay tests and 12 fake transport tests. They cover
frame component changes, invalid points, the 93-byte floor, per-frame response
keys, duplicate JSON, stream identity and termination, exact-byte transcript
changes, signer substitution, recovery bytes, the low-s bound, receipt encoding
and saved byte-count consistency. Published
EIP-191 hashes and an RFC 8032 Ed25519 vector provide independent known answers.

The fake provider exercises the complete capture path, including failure
before POST on malformed attestation, receipt and ciphertext rejection, no
output without a key, no overwrite even in a publication race, mode 0600,
allowlisted metadata and credential-free subprocess arguments/environment.
It also exercises the actual bounded curl pipe reader with a fake child.

Independent review confirmed and repaired weak Ed25519 signer acceptance by
the underlying verifier. The oracle now requires canonical points, a
nonidentity signer in the prime-order subgroup, a commitment in that subgroup
and a canonical signature scalar. Independent regression execution rejects
identity, order-two and order-four signers while valid receipts pass. Review
also verified the signed request/model replay checks. No confirmed defect
remains in the reviewed slice.

The integrated `bash gates.sh` passed with exit 0: 37 OCaml suites, 30
expected compile-fail rejections and all positive controls, existing
differential oracles, synthetic M31 replay, 28 replay tests, 12 probe tests
and cross-module `zxlint`. The build reported zero errors and warnings.
`git diff --check` and the authored-character check passed. No executable
source changed after this gate completed.

The gate calls synthetic replay and fake transport tests only; it never runs
a live probe.

## Mutation checks

All ten mutants compiled and failed unchanged behavioral assertions in the
initial M31 snapshot. Baseline and restored suites passed 27 and 11 tests, and
each restored target test passed. Source and test hashes matched that
snapshot. Later hardening is covered by the final gate's 28 and 12 tests;
the original ten-mutant campaign was not repeated after those edits.
No compile, import, setup or incidental runtime failure counted
as a kill. An initial overwrite candidate broke temporary-file cleanup; it
was excluded and replaced with a mutation that preserved cleanup while
overwriting the destination.
